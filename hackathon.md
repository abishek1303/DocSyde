# Meta Global AI Developer Hackathon Participant Guide

Source: [Cerebral Valley event details](https://cerebralvalley.ai/e/meta-ai-developer-hackathon/details).

This reference preserves the event information supplied by the user on October 28, 2026, reformatted for readability. It is not an independently verified live copy. Resource labels in the supplied text did not include destination URLs; those resources must be opened from the event page. Dates below refer to the 2026 event.

## 1. Goal and problem statements

Projects must build toward one of these problem statements:

- **Build for Your World:** Bring Meta's models into your domain. Solve a problem you know firsthand, free up time and mental space, and make something possible that was not possible before.
- **Push the Frontier:** Use Meta's models to tackle challenges in software, robotics, manufacturing, energy, materials, and beyond. Give a machine a new capability, accelerate a scientific experiment, or unlock a better way to understand and control a physical system. Show what becomes possible when these models meet the real world.

**Projects must incorporate Meta's models.** The guide lists these options:

- Muse Spark series, Muse Wonder, Muse Image, Muse Voice Transcribe, and SAM 3.1 through Meta Model API.
- Meta open-weight models Muse Glimmer and Muse Spark Open.
- Muse Code coding agent to code faster.

The viability judging stage specifically checks reasonable use of Meta Model API and/or Meta's open-weight models in the project.

## 4. Rules and eligibility

- **Open source:** Repositories must be public.
- **Team size:** Maximum four participants. Solo participants are allowed.
- **Demo scope:** Highlight only the specific features, code, and functionality built during the hackathon. Judges must be able to clearly identify original contributions. Failure to do so results in immediate disqualification at the judges' sole discretion.
- **New work only:** Presented work must have been built during the event, and submissions must make this clear. Startups may build on existing products or codebases but must identify what was newly developed during the hackathon.
- **Rights and policies:** Projects that violate legal, ethical, or platform policies, or use code, data, or assets without the necessary rights, are disqualified.

### Sample anti-projects

The guide warns against generic projects seen across many hackathons and projects that violate platform policies. The following examples are not exhaustive:

- AI-generated medical advice, such as an AI mental health advisor or skin blemish detector.
- Basic RAG applications.
- Simple image analyzers.
- Simple AI-for-education chatbots.
- AI job application screeners.
- AI nutrition coaches.
- Personality analyzers.
- Sports analyzers or coaches.
- Anything political or involving war.

## 7. Submission

**Deadline: November 4 at 9:00 PM EST via the Cerebral Valley platform. Late submissions are not considered.**

- Solo participants, teams, and startups submit through the event page's submission link.
- Each team or startup submits one project, not one submission per member.
- Each team appoints one **Representative** to represent and act on its behalf, including entering the project submission.
- Ensure the repository is publicly accessible, the video link is accessible, and everyone who worked on the project is listed on the submission page.
- Provide a **three-minute demo video** highlighting the specific features, code, and functionality built during the hackathon.
- Judges use the video as a primary artifact alongside the code and live product.

## 8. Judging

### Stage one: viability, pass/fail

The project must reasonably fit the theme and reasonably use Meta Model API and/or Meta's open-weight models to build the project during the hackathon.

### Stage two: scoring

Each criterion is scored from 0–10.

| Category | Weight | What judges assess |
| --- | --- | --- |
| Impact | 30% | Real-world potential, who benefits, how much it matters, whether people would use it, and fit with a problem statement |
| Use of Meta AI Tooling | 25% | Creative use of Meta tooling beyond a basic integration; capabilities that surprise the judges |
| Technical Depth & Execution | 20% | Sound engineering, thoughtful refinement, and craft |
| Demo | 25% | A working, impressive product that holds up live and a compelling demo video |

### Stage three: finals

The top five scoring projects per track advance. Final-round judges watch video demos live and rank projects using the same rubric.

## DocSyde context

The following connects the supplied guide to the existing project architecture; these are project planning implications, not additional event rules or implemented capabilities.

- DocSyde's documented purpose is to keep product documentation synchronized with software changes and surface it contextually inside the host application. This aligns naturally with **Build for Your World**; no competition track selection is recorded here.
- The demo should make the full change-to-documentation workflow visible: a meaningful product change, evidence from code and product context, affected documentation, an update, and its presentation inside the product.
- Meta models should perform meaningful work in that workflow. A basic RAG/chat wrapper would conflict with the guide's anti-project examples.
- Prove integrations independently before combining them, following `ARCHITECTURE.md`. PostgreSQL is implemented; repository/Git, model providers, runner, SDK, and the broader documentation workflow remain separate architectural responsibilities.
- The Baseten model identifier above is event-specific context, not a decision that Baseten must be used.
- Keep hackathon contributions identifiable and leave time for the working demo, three-minute video, public repository, and submission checks.
